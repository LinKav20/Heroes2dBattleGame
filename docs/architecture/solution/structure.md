# Структура системы

Где что лежит в репозитории, какие есть порты, реестры расширений и профили и как добавлять новое.

Обновлено 9 октября 2026.

В центре — ядро и прикладная логика. Порты объявляет прикладная логика, а порты экрана — слой визуализации. У ядра портов нет, только интерфейсы расширений. Адаптеры реализуют порты, а приложение при запуске выбирает нужные адаптеры по профилю. Чтобы добавить новую возможность, пишут новый адаптер или расширение, а центр не трогают.

## Где что лежит

| Папка | Что в ней |
|---|---|
| `libs/` | Библиотеки, из которых собирается любая конфигурация: ядро, стандартные расширения, загрузка контента, протокол, прикладная логика, слой визуализации |
| `adapters/` | Адаптеры к портам, по пакету на технологию: хранилища, каналы, агенты, политики доступа, рендереры, адаптеры интеграции |
| `apps/` | Приложения. Каждое — точка сборки: выбирает адаптеры, заполняет реестры и собирает конкретную конфигурацию из библиотек |
| `packs/` | Паки контента: наборы правил, существа, предметы, эффекты, сценарии |

Главные библиотеки: `hex` (геометрия гексов: координаты, соседи, расстояния), `kernel` (ядро), `rules-stdlib` (стандартные расширения ядра), `content` (загрузка и проверка паков), `protocol` (схемы форматов), `application` (прикладная логика и порты), `presentation` (слой визуализации).

Каждая библиотека, адаптер и пак — отдельный пакет `@heroes2dgame/…`, который публикуется в npm со своей версией. Приложения из `apps/` не публикуются. Как устроены пакеты и под какой лицензией они выходят, описано в ADR [0011](../../decisions/0011-packages-and-license.md).

Наши приложения перечислены в [окружении системы](../foundations/context.md#готовые-сборки). Потребитель, который подключает библиотеки напрямую, собирает своё приложение так же.

Зависимости направлены к центру: ядро ни от чего не зависит, в том числе от `hex`: форму поля оно получает через интерфейс топологии. `hex` тоже ни от чего не зависит, а топологию «гексы» на его основе регистрирует `rules-stdlib`. Прикладная логика зависит от ядра, адаптеры — от прикладной логики или слоя визуализации, а от приложений не зависит никто. Направление зависимостей проверяет dependency-cruiser, подробнее — в ADR [0002](../../decisions/0002-ports-adapters-microkernel.md).

## Порты

Порты объявлены в библиотеке `application`, а порты рендерера и манифеста оформления — в `presentation`. Через входящие порты систему вызывают снаружи. Через исходящие система сама обращается к внешнему миру.

### Входящие порты

| Порт | Кто вызывает | Что умеет |
|---|---|---|
| `BattlePlay` | Интерфейс, агенты | Принять команду, вернуть проекцию, подписать на пакеты событий, подсказать доступные действия, путь и прогноз. Подсказки уже отфильтрованы политикой доступа |
| `BattleHosting` | Адаптеры интеграции, потребитель при прямом подключении | Создать бой по конфигурации, продолжить сохранённый, прервать, открыть запись, вернуть результат, выгрузить журнал, сообщать об этапах жизни боя |
| `BattleHistory` | Интерфейс, просмотр записи | Показать состояние после любой записи журнала, вернуть записи в проекции актора для пошагового просмотра, начать ответвление |

### Исходящие порты

| Порт | Зачем нужен | Примеры адаптеров |
|---|---|---|
| `JournalStore` | Хранить журналы, снимки и результаты | IndexedDB, память, база данных сервера, например PostgreSQL |
| `Arbiter` | Принять команду актора и вернуть пакет событий или отказ | Локальный, который выполняет команды ядром в том же процессе; удалённый, который передаёт команду серверу |
| `Channel` | Передавать сообщения протокола в обе стороны | Память, WebSocket, BroadcastChannel для нескольких вкладок |
| `AccessPolicy` | Решить, можно ли актору отправить команду, какие стороны он видит, кто действует в текущий ход и кому направить запрос ввода | «Один актор может всё», «по таблице прав» из конфигурации боя, серверная |
| `Agent` | Принять решение от имени актора | Интерфейс человека, простой ИИ, ИИ с перебором, языковая модель, внешний бот через канал |
| `ContentSource` | Загрузить паки и сценарии | Встроенные в сборку, загрузка по HTTP |
| `Renderer` | Нарисовать поле и проиграть события | PixiJS, SVG, пустой рендерер для тестов |
| `SkinSource` | Загрузить манифест оформления, картинки и звуки | Встроенные в сборку, загрузка по HTTP |
| `Telemetry` | Сообщать о принятых и отклонённых командах, сбоях хранилища и отказах агентов. В каждом сообщении есть номер боя, номер записи и идентификатор команды | Вывод в консоль, внешняя система наблюдения, в тестах пустой |
| `Clock` | Дать время для отметок в журнале и для ограничения времени на ответ агента | Системное время, в тестах фиксированное |
| `Entropy` | Дать зерно генератора случайных чисел для нового боя | Системное, в тестах фиксированное |

Ядра в этой таблице нет: наружу оно не обращается совсем и телеметрию не пишет. Всё о его работе есть в событиях и причинах отказа. Времени ядро не знает, а случайные значения, если они есть в правилах, берёт из генератора в своём состоянии. Зерно генератора при создании боя даёт порт `Entropy`.

## Реестры расширений

Реестр — это таблица «имя — реализация». Точка сборки заполняет реестры при запуске, и дальше они не меняются.

| Реестр | Что в нём | Кто ссылается по имени |
|---|---|---|
| Операции | Урон, лечение, наложение эффекта, призыв и другие | Эффекты, способности и триггеры в контенте |
| Топологии поля | Гексы. Квадратные сетки и объёмные поля подключаются так же | Сценарии |
| Условия | Проверки вроде «соседняя клетка» или «в зоне видимости» | Контент |
| Варианты механик | Порядок ходов, расчёт атаки, этапы урона и другие механики, на которые ссылается набор правил | Наборы правил в паках |
| Миграции событий | Перевод старых версий событий в новые | Чтение журналов |
| Агенты | Виды агентов. Запасной агент из `application` точка сборки может заменить своим | Конфигурация боя, где указано, какой агент действует от имени актора |
| Политики доступа | Политики и готовые наборы прав | Профиль, конфигурация боя |
| Каналы | Каналы по схеме адреса: `memory:`, `ws:`, `broadcast:` | Профиль, настройки подключения |
| Рендереры | `pixi`, `svg`, `headless` | Профиль, настройки |
| Обработчики анимаций | Код, который проигрывает анимацию определённого вида | Манифест оформления |

Библиотека с расширениями экспортирует список своих регистраций, а точка сборки добавляет их в реестры. Имя расширения начинается с префикса библиотеки. Если имя повторяется, запуск останавливается с ошибкой.

## Профили

Профиль — это готовый набор адаптеров для одного режима работы. Точка сборки выбирает профиль по адресу страницы, по сообщению от потребителя или по настройкам окружения. Ниже — профили наших приложений. Своя точка сборки может обойтись и без профиля.

| Профиль | Арбитр | Политика доступа | Хранилище | Каналы | Агенты | Потребитель и экран |
|---|---|---|---|---|---|---|
| Одно устройство (`solo`) | Локальный | Один актор может всё | IndexedDB | В памяти | Интерфейс для одного актора, ИИ в Web Worker | Автономный режим, PixiJS |
| Бой в iframe (`iframe`) | Локальный | Из конфигурации потребителя | IndexedDB | В памяти | Как в `solo` | Адаптер интеграции iframe, PixiJS |
| Сетевой клиент (`networked`) | Удалённый | Проверяет сервер | IndexedDB как кэш копии боя | WebSocket | Интерфейс для своего актора | Адаптер интеграции iframe или автономный запуск, PixiJS |
| Сервер (`server`) | Локальный, но на сервере | Серверная | База данных | WebSocket к акторам | Серверный ИИ и языковая модель | Адаптер интеграции HTTP API; рендерера нет |
| Тесты и симуляции (`headless`) | Локальный | Любая, по тесту | В памяти | В памяти | ИИ, агенты по сценарию теста | Пустой рендерер |
| Просмотр записи (`replay`) | Нет, журнал только читается | Задаёт область видимости: полный журнал — для потребителя, проекция — для актора | IndexedDB или файл | Нет | Нет | PixiJS |

Профили `iframe` и `networked` можно совместить: потребитель открывает iframe, а клиент внутри него подключается к серверу. Если потребитель подключает библиотеки напрямую, профиль ему не нужен: он сам собирает приложение в своей точке сборки из тех же библиотек и адаптеров.

## Как добавить новое

Новая возможность — это новый адаптер или расширение и его регистрация в точке сборки. Ядро и прикладная логика не меняются.

| Что добавляем | Что делаем |
|---|---|
| Сервер | Приложение `apps/server` собирает ту же прикладную логику с адаптерами хранилища и канала, например базы данных и WebSocket. В клиенте профиль `networked` подключает удалённого арбитра. Арбитр с самого начала подключён через порт, поэтому клиент не переделываем |
| Новый транспорт, например WebRTC | Пишем пакет `adapters/channel-webrtc` с реализацией порта `Channel`. Он проходит общие тесты канала и регистрируется по схеме `rtc:` |
| Новый ИИ | Пишем пакет с реализацией порта `Agent` и регистрируем его под своим именем. Ядро без побочных эффектов, поэтому ИИ перебирает через него варианты действий |
| Новый рендерер | Пишем пакет с реализацией порта `Renderer`. Проекции и события остаются прежними |
| Новый потребитель | Потребитель выбирает готовый адаптер интеграции или подключает библиотеки напрямую. Свои данные в нашу конфигурацию боя и обратно он переводит сам |
| Новый способ интеграции | Пишем адаптер интеграции, который переводит контракт на нужный способ связи: веб-компонент, обёртку для настольного приложения, плагин игрового движка. Он проходит общие тесты контракта. Писать такой адаптер может и сторонний разработчик |
| Новая роль или схема прав | Описываем новый набор прав в конфигурации боя. Если таблицы прав мало, пишем новую политику доступа с реализацией порта `AccessPolicy` |
| Новое хранилище | Пишем пакет с реализацией порта `JournalStore`. Он проходит общие тесты хранилища |
| Новая механика | Добавляем операцию, условие или порядок ходов в `rules-stdlib` или в отдельную библиотеку и регистрируем в реестре |
| Новая форма поля, например квадраты или поле с высотами | Пишем реализацию интерфейса топологии поля и регистрируем её. Ядро и поиск пути не меняются. Чтобы показать новое поле, нужен рендерер, который умеет его рисовать |

У каждого порта есть общий набор тестов, который должен пройти любой его адаптер.
