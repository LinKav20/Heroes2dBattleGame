# Встраивание в хост

Как чужое приложение запускает наш бой и получает его результат.

Обновлено 5 октября 2026.

Хост открывает наш клиент в iframe, выбирает один из наших сценариев и передаёт параметры юнитов и права акторов. Дальше бой целиком ведёт наш клиент, а журнал и результат сохраняются у нас. Хост получает результат, при желании запрашивает журнал и сам решает, что поменять у себя. С нами хост общается только опубликованными сообщениями и о нашем коде ничего не знает.

## Кто за что отвечает

| Кто | Отвечает за |
|---|---|
| Хост | Выбирает сценарий, передаёт параметры юнитов (например, сколько здоровья осталось у персонажа после прошлого боя), перечисляет акторов, их права и агентов и переносит результат к себе |
| Наш клиент | Проверяет конфигурацию, запускает бой по сценарию, обрабатывает весь ввод и вывод во время боя, ведёт журнал, умеет показать и откатить любой шаг, собирает результат |

Свои данные в нашу конфигурацию боя и наш результат обратно в свои данные переводит хост. Под форматы конкретных хостов мы не подстраиваемся.

## Адрес встраивания

Хост открывает iframe по адресу встраивания, например `https://<наш-домен>/embed`. Клиент запускается в профиле `embedded` и общается с хостом через мост к хосту — это порт `HostBridge` с адаптером на `postMessage`.

## Сообщения

| Сообщение | Кто кому | Когда |
|---|---|---|
| `ready` | Клиент хосту | Клиент загрузился. Сообщает версию протокола |
| `createBattle` | Хост клиенту | Создать новый бой. Содержит конфигурацию боя |
| `resumeBattle` | Хост клиенту | Продолжить сохранённый бой по его номеру |
| `openReplay` | Хост клиенту | Открыть законченный бой для просмотра |
| `battleStarted` | Клиент хосту | Бой создан. Содержит номер боя |
| `battleProgress` | Клиент хосту | Необязательное сообщение с номером раунда и последней записи журнала, чтобы хост мог показать, как идёт бой |
| `battleFinished` | Клиент хосту | Бой закончился. Содержит результат |
| `getJournal` | Хост клиенту | Запросить журнал |
| `journal` | Клиент хосту | Журнал боя |
| `error` | Клиент хосту | Что-то пошло не так. Содержит список причин |

Форматы сообщений описаны в [справочнике](../../reference/protocol.md).

## Что хост передаёт

Хост указывает номер нашего сценария и параметры юнитов поверх данных сценария: текущее здоровье, действующие эффекты, инвентарь, сколько раз уже использованы способности. Так последствия прошлых событий кампании переходят в бой.

Ещё хост перечисляет акторов. Для каждого он указывает права (готовый набор — «ведущий», «командующий» или «наблюдатель» — или свой) и агента, который будет действовать от его имени: интерфейс, ИИ или удалённый клиент в сетевом бою. Хост может поменять настройки набора правил, например какие броски вводятся извне, и задать фиксированное зерно генератора.

Настройки экрана — язык, оформление, скорость анимаций — хост передаёт отдельно от конфигурации боя. На ход боя они не влияют и в журнал не попадают.

Наконец, хост может передать свою метку — любую строку, например «кампания 42, сессия 7, встреча 3». Мы её не разбираем, а возвращаем в результате, чтобы хост знал, к чему этот результат относится.

Если в конфигурации ошибка, хост получает `error` со списком причин, и бой не создаётся. Пример конфигурации есть в [справочнике](../../reference/examples.md).

## Что хост получает

В результате боя есть:

- исход: победа, поражение или ничья, кто победил и по какому условию;
- сколько длился бой в раундах;
- что стало с каждым юнитом: жив ли, сколько существ было и осталось, сколько здоровья, какие эффекты действуют, что изменилось в инвентаре и сколько раз применены способности;
- призванные существа и потери;
- значения переменных сценария;
- хеш итогового состояния.

Журнал бывает большим, поэтому его хост запрашивает отдельно.

## Встраивание с сервером

Для сетевого боя хост создаёт бой через HTTP API сервера и получает ссылку на каждого актора. Одну ссылку хост обычно открывает у себя в iframe, а остальные раздаёт людям. Результат и журнал можно получить и через `postMessage` в iframe, и через HTTP API сервера.

## Безопасность

Наш хостинг отдаёт заголовок `Content-Security-Policy: frame-ancestors` со списком хостов, которым разрешено нас встраивать.

Мост проверяет `origin` у каждого входящего сообщения и отправляет сообщения только на точный адрес хоста, никогда на `*`. Каждое входящее сообщение сверяется со схемой протокола.

Токены акторов не попадают ни в журналы, ни в логи.

## Версии протокола

У протокола встраивания своя версия, и клиент сообщает её в `ready`. Новые поля мы добавляем так, чтобы старые хосты продолжали работать. Если без несовместимых изменений не обойтись, выпускаем новую версию протокола, а старую ещё какое-то время поддерживаем.
