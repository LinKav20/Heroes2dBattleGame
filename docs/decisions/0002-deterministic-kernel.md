# 0002. Детерминированное ядро и ввод через запросы

Ядро пишем на TypeScript из функций без побочных эффектов, и на одном входе оно всегда даёт один результат. Команда выполняется по шагам из стека, который хранится в состоянии. Кубики ядро бросает само генератором, состояние которого хранится в состоянии боя. Когда ядру нужны данные извне, например результат настоящих кубиков, оно записывает запрос ввода и останавливается. Цена — внутри ядра нельзя пользоваться случайностью, текущим временем и дробной арифметикой, а выполнение команды устроено сложнее.

## Задача

Один и тот же бой должен давать один и тот же результат при повторе, на сервере и в каждой копии боя. ИИ должен перебирать варианты, вызывая правила на копии состояния, а тесты — работать без браузера.

Посреди действия ядру бывают нужны данные извне: результат броска, выбор цели, выбор варианта. Если ядро будет ждать ответа, бой нельзя будет сохранить или передать в этот момент. Часть кубиков люди хотят бросать сами, часть удобнее доверить генератору, и откат не должен позволять перебросить кубик.

## Варианты

1. Правила живут в интерфейсе или в игровом фреймворке, и ядро ждёт ввода блокировкой или промисом. Правила не запустить на сервере и в тестах, а состояние не сохранить в момент ожидания.
2. Отдельные реализации правил для клиента и сервера, а генератор встроен в правила, ручной ввод — особый случай. Реализации разойдутся, а в коде появятся два пути для бросков.
3. Одно ядро без побочных эффектов. Генератор хранится в состоянии боя, а ожидание внешнего ввода — как запрос в том же состоянии.

## Решение

Выбираем третий вариант.

У ядра две главные функции: одна получает состояние и команду и возвращает события, другая получает состояние и событие и возвращает новое состояние. В ядре нет DOM, API Node.js, `Math.random`, текущего времени и дробных чисел в игровой арифметике. Времени ядро не знает: отметки времени и время на ответ агентов живут в прикладном слое.

Команда раскладывается на шаги, которые лежат в стеке внутри состояния. В шагах только данные, без функций. Если шагу нужны данные извне, ядро записывает запрос ввода и останавливается, а ответ приходит отдельной командой.

Для каждого назначения броска набор правил говорит, откуда берётся значение: из генератора или извне. Бросок из генератора ядро делает само и записывает результат в событие. Для внешнего броска ядро записывает запрос ввода. Кто на него ответит, решает политика доступа (см. [0004](0004-arbiter-and-access.md)), а что делать, если никто не ответил, — запасной агент. Ядро этого не знает.

## Последствия

Правила написаны один раз и работают везде. Бой воспроизводится, тесты простые, ИИ перебирает варианты через то же ядро. Бой можно сохранить и передать в любой момент, даже пока ядро ждёт ввода. Генератор восстанавливается при откате, поэтому перебросить кубик нельзя, а сделать бросок ручным можно одной настройкой.

Взамен нужна дисциплина: целочисленная арифметика, предсказуемый порядок обхода коллекций, все входные данные передаются явно. Глубину стека шагов нужно ограничить, чтобы цепочки триггеров не зацикливались.

## Как проверяем

Линтер запрещает в ядре `Math.random`, `Date.now`, DOM и API Node.js. CI проигрывает эталонные журналы в браузере, в Web Worker и в Node.js и сравнивает хеши. Тест сохраняет состояние с открытым запросом ввода, загружает его, отвечает на запрос и сверяет результат с боем без перерыва. Ещё один тест проводит бой с бросками генератора и тот же бой с ручным вводом тех же значений и сравнивает журналы.
