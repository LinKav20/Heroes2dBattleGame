# 0004. Журнал событий как основа истории боя

Чтобы бой можно было проиграть по шагам, откатить и передать хосту, мы храним бой как журнал команд и событий с результатами, принимая необходимость версионировать формат событий.

## Контекст и проблема

Нужны: повтор каждого шага, откат к любому шагу, восстановление после перезагрузки, синхронизация реплик, передача истории хосту. Хранение только текущего состояния этого не даёт.

## Рассмотренные варианты

1. Хранить только текущее состояние и снимки по требованию. Нет истории и аудита.
2. Хранить только команды и пересчитывать правила при повторе. Повтор ломается при изменении правил, нужно повторять броски.
3. Хранить команды и события с результатами, плюс контрольные точки.

## Решение

Мы выбираем третий вариант. Журнал только дополняется. Каждая запись: номер, эпоха, команда, отправитель, пакет событий, хеш состояния. События хранят результаты, поэтому повтор не вызывает правила и не бросает кубики. Откат — запись в журнале, история не стирается. Отдельной базы для чтения нет: срезы строятся из состояния в памяти.

## Последствия

- Хорошо: повтор, откат, аудит, передача хосту, синхронизация реплик одним механизмом.
- Плохо: формат событий нужно версионировать и поддерживать миграции.
- Плохо: журнал растёт; нужны контрольные точки.

## Как проверяем

Тест: повтор журнала даёт то же состояние, что живой бой. Тест миграций на журналах старых версий.
