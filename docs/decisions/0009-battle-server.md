# 0009. Сервер боёв — одно приложение, первая реализация на Node.js

Сервер делаем одним приложением без микросервисов. Первую реализацию пишем на Node.js из тех же библиотек, что и клиент, с каналом WebSocket и базой данных. Так сетевой бой сразу использует то же ядро. Снаружи сервер виден только через протокол боя и HTTP API, поэтому свой сервер на любом языке может написать кто угодно. Цена — все соединения одного боя должны приходить в тот экземпляр сервера, который этот бой ведёт.

## Задача

Для сетевой игры нужен арбитр на сервере. Команда небольшая, а клиенту для боя без сервера ядро нужно в любом случае.

## Варианты

1. Сразу писать сервер на другом языке. С первого дня придётся писать и поддерживать две реализации ядра: в клиенте для боя без сервера и на сервере.
2. Микросервисы. Для нашего масштаба это лишнее.
3. Одно приложение на Node.js из тех же библиотек, что и клиент. Протокол и форматы при этом не зависят от языка.

## Решение

Выбираем третий вариант. Сервер — это приложение `apps/server`, точка сборки с адаптером хранилища, адаптером канала, серверной политикой доступа и адаптером интеграции. База данных подключается адаптером хранилища, поэтому её можно выбрать любую, например PostgreSQL. От неё нужны только транзакции и уникальные ключи. С акторами сервер общается через порт `Channel`: первый адаптер работает по WebSocket, но подойдёт любой двусторонний транспорт. С потребителями сервер общается через адаптер интеграции, и первый такой адаптер — HTTP API.

Клиенты и боты общаются с сервером только по протоколу боя, а потребители — через контракт интеграции. Форматы того и другого опубликованы в виде JSON Schema и не зависят от транспорта. Поэтому любой может написать свой сервер для своего приложения на другом языке и с другой базой данных (см. [0001](0001-language-independence.md)). Его правила не обязаны совпадать с нашими: команды одного боя принимает только один арбитр, а клиенты применяют присланные события и правила заново не считают.

Сервер ведёт сколько угодно боёв одновременно и без доработок работает в нескольких экземплярах: бои распределяются между экземплярами по номеру боя. Что для этого нужно от инфраструктуры и что происходит, если экземпляр остановился, описано в [развёртывании](../architecture/solution/deployment.md#с-сервером). Очередь команд одного боя и эпоха описаны в [акторах и синхронизации](../architecture/topics/actors-and-sync.md#версии-и-параллельные-команды).

## Последствия

Прикладная логика и ядро общие с клиентом, а инфраструктура простая. Другой сервер можно написать, не меняя протокол. Подсказки клиент считает своим ядром, поэтому если правила сервера отличаются от правил клиента, подсказки могут не совпасть с тем, что примет сервер.

Для долгих соединений нужен хостинг, который их поддерживает.

## Как проверяем

Сценарные тесты прогоняются на серверной сборке. Тест проводит много боёв одновременно и сравнивает их журналы с журналами тех же боёв, проведённых по одному. Проверка зависимостей не даёт приложению сервера зависеть от библиотек и адаптеров интерфейса.
