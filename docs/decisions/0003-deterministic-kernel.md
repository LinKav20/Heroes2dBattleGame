# 0003. Детерминированное ядро и ввод через запросы

Первую реализацию ядра пишем на TypeScript из функций без побочных эффектов, и на одном входе оно всегда даёт один результат. Команда выполняется по шагам из стека, который хранится в состоянии. Случайные значения, если они есть в правилах, ядро берёт из генератора случайных чисел в состоянии боя. Когда ядру нужны данные извне, например результат настоящих кубиков, оно записывает запрос ввода и останавливается. Цена — внутри ядра нельзя пользоваться системной случайностью, текущим временем и дробной арифметикой, а выполнение команды устроено сложнее.

## Задача

Один и тот же бой должен давать один и тот же результат при повторе, на сервере и в каждой копии боя. ИИ должен перебирать варианты, вызывая правила на копии состояния, а тесты — работать без браузера.

Посреди действия ядру бывают нужны данные извне: результат броска, выбор цели, выбор варианта. Если ядро будет ждать ответа, бой нельзя будет сохранить или передать в этот момент. Часть кубиков люди хотят бросать сами, часть удобнее доверить генератору, и откат не должен позволять перебросить кубик.

## Варианты

1. Правила находятся в интерфейсе или в игровом фреймворке, и ядро ждёт ввода блокировкой или промисом. Правила не запустить на сервере и в тестах, а состояние не сохранить в момент ожидания.
2. Отдельные реализации правил для клиента и сервера; генератор встроен в правила, а ручной ввод — особый случай. Реализации разойдутся, а в коде появятся два пути для бросков.
3. Одно ядро без побочных эффектов. Генератор хранится в состоянии боя, а ожидание внешнего ввода записывается запросом в том же состоянии.

## Решение

Выбираем третий вариант.

У ядра две главные функции: одна получает состояние и команду и возвращает события, другая получает состояние и событие и возвращает новое состояние. В ядре нет DOM, API Node.js, `Math.random`, текущего времени и дробных чисел в игровой арифметике. Времени ядро не знает: отметки времени ставит, а время на ответ агентов отсчитывает прикладная логика.

Команда раскладывается на шаги, которые хранятся в стеке внутри состояния. В шагах только данные, без функций. Если шагу нужны данные извне, ядро записывает запрос ввода и останавливается, а ответ приходит отдельной командой.

Случайность в правилах необязательна: если набор правил её не использует, генератора нет. Если случайные значения есть, набор правил для каждого говорит, откуда оно берётся: из генератора или извне, а потребитель может поменять источник в конфигурации боя. Бросок из генератора ядро делает само и записывает результат в событие. Для внешнего броска ядро записывает запрос ввода. Кто на него ответит, решает политика доступа (см. [0005](0005-arbiter-and-access.md)), а что делать, если никто не ответил, — запасной агент. Ядро этого не знает.

## Последствия

Правила написаны один раз и одинаково работают в браузере, на сервере и в тестах. Бой воспроизводится, тесты простые, ИИ перебирает варианты через то же ядро. Бой можно сохранить и передать в любой момент, даже пока ядро ждёт ввода. Генератор восстанавливается при откате, поэтому перебросить кубик нельзя, а сделать бросок ручным можно одной настройкой.

Взамен нужна дисциплина: целочисленная арифметика, предсказуемый порядок обхода коллекций и явно переданные входные данные. Глубину стека шагов нужно ограничить, чтобы цепочки триггеров не зацикливались.

## Как проверяем

Линтер запрещает в ядре `Math.random`, `Date.now`, DOM и API Node.js. Тесты проигрывают эталонные журналы двумя способами — применяя записанные события и заново выполняя записанные команды — и сравнивают хеши состояния. Тест сохраняет состояние с открытым запросом ввода, загружает его, отвечает на запрос и сверяет результат с боем без перерыва. Ещё один тест проводит один и тот же бой дважды, с бросками генератора и с ручным вводом тех же значений, и сравнивает журналы.
